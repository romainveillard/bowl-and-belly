# Bowl & Belly

Self-hosted PWA for tracking pets' food intake (calories against a daily target) and weight. MIT licence, published as amd64 and arm64 Docker images.

`docs/design.md` is the source of truth for scope, data model and UX. Read the relevant section before changing behaviour, and update it in the same PR when a decision changes.

## Stack

- Backend: Node, Hono (Node adapter), TypeScript strict, Zod validation, SQLite via Drizzle ORM.
- Frontend: React SPA built with Vite, TanStack Query, Recharts, i18next (en-GB, fr). Calls the API through Hono's typed RPC client.
- One container serves the API and the built frontend; one volume holds the SQLite file.

## Commands

- Install: `npm install`
- Dev: `npm run dev` (API on port 3000, Vite on port 5173 proxying `/api`; open the Vite one)
- Test: `npm test`
- Lint and typecheck: `npm run lint`, `npm run format:check` and `npm run typecheck` (`npm run format` rewrites files)
- Production build: `npm run build`, then `npm start`
- Generate a migration: `npm run db:generate` (Drizzle Kit; never hand-edit generated SQL)

## Domain invariants

- Weights and amounts are integer grams. Timestamps are stored in UTC; which day an entry belongs to comes from the app time zone and "day starts at" setting.
- Feed entries snapshot `kcal_per_kg` from the food. Editing a food's kcal only rewrites past entries when the user chooses to.
- Logging, editing and deleting a feed entry adjust the food's stock by the difference; deleting returns the net amount (served minus leftover already returned).
- Daily targets are a per-pet history (`pet_target`), never stored per feed entry.
- Rows with a `system_key` (seeded pet and food types) are read-only and labelled through translation keys.
- The API returns codes and machine values, never user-facing sentences.

## Prose style

- British English everywhere: comments, docs, commit messages, PR descriptions and the English UI strings (organisation, behaviour, colour, licence as a noun).
- Keep spellings forced by the wire: code identifiers, URL paths, third-party field names, HTTP headers.

## Comments

Comment only the why the code can't express: invariants, external quirks, deliberate deviations from idiom, load-bearing test-fixture values. Don't restate what the code does or market the design. Design rationale belongs in the commit or PR. Default to no comment.

## Tests

- Only test code with real logic in it: calculations (calorie targets, daily totals, stock adjustments, day boundaries), branching rules and invariants. Don't add tests for simple things such as plain CRUD routes, field mapping, wiring or rendering static markup.
- A test must pin something the type system can't: a non-obvious translation, a contract or invariant, a deliberate decision, a real boundary.
- No tautologies, no tests that silently stop covering new variants, no pure pass-through delegation tests. When wiring a new value distinction through a shared path, add a fixture with distinct values.
- Match the existing test file's style. If it inlines all setup, keep inlining rather than adding a shared helper.

## Design and placement

- YAGNI on new fields: a new schema, DTO or response shape carries only what its immediate consumer reads or writes. Collapse one-field wrappers to the primitive.
- Before writing a new route, query, hook or helper, look at its two or three nearest peers and match their shape.
- Mirror a neighbour's structure, not its flaws. If the analogue has a bug, write the better version and point out the asymmetry.
- When fixing a shared boundary (schema, helper, format), find every consumer and make sure each has a test that exercises it.

## Commits and PRs

- One PR per feature is the norm. Only split a PR when a specific change calls for it, decided case by case, not by default.
- Small logical commits within a PR, split by theme; each should build on its own.
- DB migrations get their own commit. Frontend work gets its own commit when a PR touches both sides.
- Stage files by name; never `git add -A` or `git add .`.
- PR descriptions use `.github/pull_request_template.md`, keeping all its `###` headings and ticking only checklist items that are actually done.
- PR descriptions are written for humans in the author's voice: succinct, at most three bullets per list. No "generated by" or co-author notes in PR bodies (commit trailers are fine).
- Never post PR comments or replies, including to bots, without explicit permission. Push the fix and propose the reply instead.
